# バックアップと復元

## 最初に理解しておくこと

**HoshID のバックアップは「DB のダンプ」だけでは成立しない。**

DB の中には `BETTER_AUTH_SECRET` で暗号化された値が入っている。署名鍵の秘密鍵、
二要素認証の TOTP シークレットとバックアップコードがそれにあたる。ダンプだけを
戻しても、当時の秘密が無ければ**復元は成功したように見えて中身が読めない**。

```
DB のダンプ  +  その時点のルート秘密  =  復元できる
DB のダンプ  のみ                      =  復元できない
```

しかも壊れ方が悪い。**復元した人は気づけず、利用者が踏んで初めて分かる。**
ログインしようとした人が二要素認証で詰まる、トークン発行が「秘密鍵を復号
できない」で落ちる、という形で出る。

だからこの2つは**組で管理する**。そして
**別々の場所に保管する**（同じ場所に置くと、片方が失われるとき両方失う）。

---

## 何を取るか

| 対象 | 置き場所 | 取り方 |
|---|---|---|
| データベース | PostgreSQL | `pg_dump`（後述） |
| ルート秘密 | 環境変数 / k8s Secret | 秘密管理の仕組みで別途 |

DB に入っていて、失うと戻せないもの:

- アカウント、パスワードのハッシュ、ロール、ステータス
- パスキーの公開鍵、二要素認証の設定
- **アイコン画像**（`avatar` テーブルにバイト列で入っている。ファイルとして
  外に置いていないので、DB を戻せば画像も戻る。代わりにダンプは大きくなる）
- OAuth クライアントの登録と、利用者が与えた同意
- お知らせ、Webhook の設定、監査ログ
- 署名鍵（`jwks`）

アプリのコードと設定はリポジトリにあるので、バックアップの対象ではない。

## 取る

```bash
pg_dump \
  --format=custom \
  --no-owner \
  --no-privileges \
  --file="hoshid-$(date +%Y%m%d-%H%M%S).dump" \
  "$DATABASE_URL"
```

- **`--format=custom`** を使う。並列復元ができ、必要なテーブルだけ取り出せる。
- `--no-owner` / `--no-privileges` で、復元先のロール名に縛られなくする。
- **`pg_dump` のバージョンは DB と合わせる**（PostgreSQL 17）。古い
  `pg_dump` で新しいサーバを取るとエラーになる。

### どのくらいの頻度で

| | 目安 |
|---|---|
| 頻度 | 1日1回。加えて、**メンバーを大量に承認した直後**や**秘密を入れ替えた直後**は手動で1回 |
| 保持 | 日次7世代 + 週次4世代。アイコン画像の分だけ膨らむので、容量を見て調整する |
| 保管先 | DB サーバとは別のホスト。ルート秘密とはさらに別の場所 |

### 暗号化

**ダンプはパスワードハッシュと、暗号化された 2FA シークレットの塊である。**
保管先が自分の管理下にないなら（オブジェクトストレージなど）、置く前に暗号化
すること。

```bash
pg_dump --format=custom --no-owner --no-privileges "$DATABASE_URL" \
  | age -r "$AGE_RECIPIENT" > "hoshid-$(date +%Y%m%d).dump.age"
```

**この暗号鍵を、ルート秘密と同じ場所に置かないこと。** 片方を取られたときに
両方使えてしまう。

## 戻す

**手順を最後まで通すこと。** 途中で止めると、読めない暗号文を抱えたまま
運用が始まる。

**1. 当時のルート秘密を用意する。** これが無ければ先に進まない。ダンプの
日付に対応する値を確認する。

**2. 空の DB に復元する。**

```bash
createdb hoshid_restore
pg_restore --no-owner --no-privileges --dbname=hoshid_restore hoshid-YYYYMMDD.dump
```

**3. 秘密が合っているか確かめる。**

```bash
DATABASE_URL=postgres://.../hoshid_restore \
BETTER_AUTH_SECRET=<当時の値> \
  bun run verify:secrets
```

暗号文を全部復号してみて、読めないものがあれば止まる。
**ここが通らないうちはアプリを向けないこと。**

秘密を入れ替えている途中のダンプなら、当時読めた版をすべて
`BETTER_AUTH_SECRETS` に並べる（手順は
[key-rotation.md](key-rotation.md)）。

**4. スキーマと鍵を今の状態に合わせる。**

```bash
bun run deploy:prepare
```

マイグレーションの適用と、鍵の保守を行う。古いダンプの署名鍵は公開期限を
過ぎていることがあるが、その場合は次の署名で新しい鍵が作られるので放って
おいてよい。

**5. アプリを向けて、実際に確かめる。**

- ログインできるか（パスワード / パスキー）
- 二要素認証を設定しているアカウントで通るか
- RP から認可フローが通るか（`bun run e2e`）

### 復元したあと、利用者に起きること

- **ダンプ以降に申請・承認されたアカウントは消えている。** 再申請が要る。
- **ダンプ以降のセッションは無効**になり、全員ログインし直しになる。
- **逆に、ダンプ以降に失効させたセッションが復活する。** 不正アクセスへの
  対応で端末を失効させていた場合、その端末がまた有効になる。心当たりがあれば
  復元後にもう一度失効させること。
- ダンプ以降の監査ログは失われる。**何が起きたかを追う必要がある状況なら、
  復元する前にいまの DB のダンプを取っておくこと。**

---

## 試す

**復元したことがないバックアップは、バックアップではない。**

取れているつもりで中身が空だった、`pg_dump` のバージョンが違って戻せない、
当時の秘密が見つからない——どれも、試していなければ本番で初めて分かる。

**3か月に1回**、上の手順を最後まで通す。確認するのは次の3点。

1. ダンプから空の DB へ復元できる
2. `bun run verify:secrets` が通る（秘密とダンプが組になっている）
3. 復元した DB に向けて、実際にログインできる

試した日付と、使ったダンプの日付を記録に残す。

---

## やってはいけないこと

- **ダンプとルート秘密を同じ場所に置く。** 片方が漏れれば両方漏れ、片方を
  失えば両方失う。
- **本番の DB に直接 `pg_restore` する。** 空の DB に戻してから確認し、
  それから切り替える。
- **秘密を確認せずに復元を始める。** 一番時間を失うのがこの順序間違い。
- **稼働中の Pod から `pg_dump` を叩いて、そのままコンテナ内に置く。**
  Pod が消えるとダンプも消える。
- **ダンプを取っただけで安心する。** 試していないものは動かない。

## まとめ

| 状況 | すること |
|---|---|
| 平常時 | 日次ダンプ。ルート秘密は別の場所に保管 |
| 承認をまとめて行った / 秘密を入れ替えた | 手動でもう1回取る |
| 復元する | 当時の秘密を用意 → 空の DB に復元 → `verify:secrets` → `deploy:prepare` → 実際にログイン |
| 3か月ごと | 復元を最後まで試す |
