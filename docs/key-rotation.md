# 鍵の運用

HoshID には**性質の違う鍵が2種類**ある。混同すると事故の規模を読み違える。

| | 署名鍵（JWKS） | ルート秘密（`BETTER_AUTH_SECRET`） |
|---|---|---|
| 役割 | ID トークン・アクセストークンに署名する | DB に保存する秘密を暗号化する |
| 保管先 | DB の `jwks` テーブル（秘密鍵は暗号化済み） | 環境変数 |
| 入れ替え | **90日ごとに自動** | **定期的には行わない**（後述） |
| 失うと | その鍵で署名したトークンが検証不能 | **2FA・JWKS 秘密鍵・保存中の全ての暗号文が読めなくなる** |

## 覚えておかなくてよいようにしてある

鍵の問題は**放っておいても何も起きない**のが厄介なところで、自動ローテーションが始まっていなくても、古い秘密を捨てられないままでも、画面は普通に動き続ける。だから人の記憶に頼らない作りにしてある。

| | いつ | 何を |
|---|---|---|
| デプロイ時の保守処理 | `bun run deploy:prepare`（マイグレーションと同じ場所） | 期限の設定・再暗号化・古い行の削除。**べき等** |
| 起動時の点検 | サーバ起動のたび | 問題があればログに警告。何も書き換えない |
| 管理画面 | `/lounge/admin/keys` | 鍵の状態と、対処が要ることの一覧 |

**Pod に `exec` で入って手で叩く運用にはしない。** 手で叩くのは、予定を早めたいときと事故のときだけ。

## 1. 署名鍵（JWKS）

### 仕組み

`lib/auth.ts` の `jwt()` に2つの期間を設定してある。値と根拠は `lib/jwks.ts`。

```
作成 ─────── 署名に使われる（90日） ───────┤
                                          └─ 検証のためだけに公開（7日） ──┤
                                                                          └─ JWKS から消える
```

- **署名**には「期限内で最も新しい鍵」が選ばれる。
- 期限内の鍵が1本も無くなると、Better Auth が**次の署名のときに新しい鍵をその場で作る**。運用者が何もしなくても回る。
- 退役した鍵は猶予期間のあいだ JWKS に残る。**この間に、その鍵で署名された発行済みトークンが寿命を迎える。**

猶予期間（7日）は、HoshID が発行する最も長生きするトークン＝**ID トークンの10時間**を大きく上回る必要がある。ここを縮めると、まだ有効期限内のトークンが「署名した鍵が JWKS に無い」という理由で突然弾かれ、RP 側からは原因が全く見えない壊れ方をする。`idTokenExpiresIn` を延ばすときは猶予期間も併せて見直すこと。

### 平常時にすること

**何もしない。** 90日ごとに勝手に入れ替わる。cron も要らない。

状態を見たいときは管理画面（`/lounge/admin/keys`）か、端末なら:

```bash
bun run jwks
```

### デプロイ時に自動で走ること

```bash
bun run keys:maintain      # deploy:prepare に含まれる
```

3つだけ行う。どれも**何度実行してもよく、実行しても利用者に影響が出ない**。

1. **期限の無い鍵に期限を打つ。** `rotationInterval` は新しく作る鍵にしか効かないので、設定を入れる前からある鍵は期限が空のままになる。**このままだと自動ローテーションが一生始まらないのに、エラーは何も出ない。** ここで拾う。
2. **古い版のままの暗号文を現行版へ書き換える**（2. を参照）。
3. **公開の終わった鍵の行を消す。**

**鍵の交換と失効はここでやらない。** 交換は期限が来れば勝手に行われるし、失効は人が判断すべきこと。デプロイのたびに鍵が変わる状態にはしない。

### 予定を待たずに交換する

```bash
bun run jwks --rotate
```

新しい鍵を作り、それまでの鍵を退役させる。古い鍵は消さず猶予期間に入るので、**発行済みトークンは壊れない**。RP 側は未知の `kid` を見た時点で JWKS を取り直すので、設定変更も再起動も要らない。

### 漏洩したとき

```bash
bun run jwks --revoke <kid>
```

**その鍵を JWKS から即座に削除する。** 猶予期間を与えない。その鍵で署名されたトークンは全て検証できなくなり、利用者は認証をやり直すことになる。漏れた鍵で偽のトークンを作られている可能性がある以上、それが正しい。

削除後に署名できる鍵が残らない場合は、先に新しい鍵を作ってから消す。自動生成に任せると、生成の失敗が「利用者のログインが落ちる」という形で現れるため。

DB のダンプが流出したのなら、`BETTER_AUTH_SECRET` も漏れたとみなして 2. へ進む。

### 変更が正しいか確かめる

```bash
bun run verify:jwks
```

スクリプトが作る鍵を、サーバと同じ経路で復号・署名・検証できるかを確認する。確認用の鍵は最後に削除するので DB には残らない。**鍵まわりのコードや秘密の構成を変えたら、これを通してから本番に出すこと。**

## 2. ルート秘密（`BETTER_AUTH_SECRET`）

### 何が人質になっているか

この値から導かれる鍵で、**DB の中の次のものが暗号化されている**。

- JWKS の秘密鍵
- **二要素認証の TOTP シークレットとバックアップコード**
- メール OTP のトークン
- OAuth の `state` など、往復のあいだ預かる値

**単純に差し替えると、二要素認証を設定している全員が締め出される。** 署名鍵だけの問題ではないので、「トークンが作り直されるだけ」と考えないこと。

### 定期的には入れ替えない

署名鍵と違い、**これをカレンダーで回すことに意味はない。**

- **露出面が違う。** 署名鍵は公開鍵が配られ、攻撃者が手に取れるトークンに署名する。ルート秘密は環境変数にあるだけで、ネットワークに出ない。
- **版を足しても、既存の暗号文は書き換わらない。** Better Auth が版を使うのは新しく書くときだけ。だから「版を足す」だけを繰り返しても、古い秘密は読める状態で残し続けるしかなく、**漏れたときの被害範囲は縮まらない。**

入れ替えが意味を持つのは、次の**再暗号化まで終えたとき**だけ。そこまでやって初めて古い版を捨てられる。

したがってこれは**事故が起きたときにやること**であって、定期作業ではない。想定する引き金は、DB ダンプの流出、権限を持つ人の離脱、誤ってリポジトリに入れた、など。

### 入れ替える手順

```bash
openssl rand -base64 32     # 新しい秘密を作る
```

各段階でデプロイし、動作を確認してから次へ進む。

**1. 版を付け始める。** 既存の `BETTER_AUTH_SECRET` はそのまま残し、新しい値を版1として足す。

```
BETTER_AUTH_SECRET=<いまの値。まだ消さない>
BETTER_AUTH_SECRETS=1:<新しい値>
```

以後の書き込みは版1で暗号化される。版の付いていない古い暗号文は `BETTER_AUTH_SECRET` で読まれる（これが `legacySecret` の役割）。

**2. 再暗号化する。** デプロイ時の保守処理に含まれているので、通常は自動で終わる。手で確認したい場合は:

```bash
bun run secrets:reencrypt --dry     # 何が書き換わるか見る
bun run secrets:reencrypt           # 書き換える
```

**読めない行は触らずに飛ばす**（上書きすると復旧できなくなるため）。飛ばした行があれば警告が出る。その場合は**古い版をまだ外さないこと。**

**3. 確認する。** 管理画面の「ルート秘密」で、古い版・版なしがどちらも 0 件になっていること。`bun run verify:jwks` を通し、ログインと二要素認証を実際に試す。

**4. 古い値を外す。**

```
BETTER_AUTH_SECRETS=1:<新しい値>
# BETTER_AUTH_SECRET は削除
```

**5. 次からは版を重ねる。** 先頭が現行。同じ手順（足す → 再暗号化 → 確認 → 外す）を繰り返す。

```
BETTER_AUTH_SECRETS=2:<さらに新しい値>,1:<ひとつ前の値>
```

### 漏洩したとき

版を足すだけでは足りない。古い秘密で暗号化されたものは、漏れた秘密で読めるままだから。

1. `BETTER_AUTH_SECRETS` に新しい版を足し、先頭に置く
2. 再暗号化を完了させ、**古い版を外す**（読めなくするのが目的）
3. `bun run jwks --revoke <kid>` で署名鍵を全て捨て、新しい鍵に置き換える
4. 全セッションを失効させる
5. **二要素認証を設定している利用者に、再設定を依頼する。** シークレットが漏れている以上、そのコードはもう第二要素として機能しない

### やってはいけないこと

- **`BETTER_AUTH_SECRET` を予告なく差し替える。** 復号できない暗号文は `Failed to decrypt private key` などで落ちる。署名鍵は作り直せて済むが、TOTP シークレットは作り直せない。
- **再暗号化が終わる前に古い版を外す。** とくに TOTP シークレットは利用者が二要素認証を設定し直すまで書き換わらないので、飛ばされた行が残っていないかを必ず確認する。
- **バックアップを取らずに運用する。** k8s Secret の値そのものを、DB のバックアップとは**別の場所**に保管する。同じ場所に置くと、片方が失われたときに両方失う。
- **DB のバックアップから復元するとき、当時の秘密を用意せずに戻す。** バックアップと秘密は組で管理する。

## まとめ

| 状況 | すること |
|---|---|
| 平常時 | 何もしない。署名鍵は自動で回る |
| デプロイ | `bun run deploy:prepare`（保守処理を含む） |
| 署名鍵を早めに替えたい | `bun run jwks --rotate` |
| 署名鍵が漏れた | `bun run jwks --revoke <kid>` |
| ルート秘密を替えたい | 版を足す → 再暗号化 → 確認 → 古い版を外す |
| ルート秘密が漏れた | 上記 → 署名鍵を全廃 → 全セッション失効 → **2FA の再設定を依頼** |
